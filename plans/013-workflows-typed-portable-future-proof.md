## Why this matters

- The developer wants workflows to be "ultra robust": a typed value arrives with its type or the
  step fails with a clear error; a workflow can move between computers and servers, be shared,
  survive upgrades and downgrades in the support window, and get new node kinds with no data loss.
- Typed answers shipped in v0.76.0 (#14192, 2026-11-21) after a user request on X. They depend on
  free-text parsing, and several paths give `""` with no error.
- The graph has no format version. Only the SQL `CHECK` constraints of migration 0046 act as one.
  Changes with no migration (new field, value type, trigger type, output target, limit, rule) have
  no guard. 20 format changes in 4 weeks; 6 had no gate, and 4 changed a meaning in place.
- Workflows already use 18 Team API capabilities, one for each feature.
- There is no export or import for one workflow. Instance transfer is the only path between
  computers, and it has a live bug (item 1).

## Developer decisions

On 2026-11-22 the developer accepted the defaults below ("do all as you see fit").

### 1. A cleared chat link does not match every chat

Evidence: `src/main/instance-transfer-workflows.ts:72` sets `fields.connectionId = ""`.
`src/backend/workflows/telegram-matching.ts:31` reads `""` as "any linked chat"
(`if (connectionId && connectionId !== mention.connectionId) return false;`). Slack and Discord
outputs fall back to the trigger's workspace (`slack-matching.ts:103-104`, from the audit).
`placeId` and `roles` are kept (`hasConnection`, `:78-81`).

Change: write an explicit unlinked marker that no matcher accepts, clear `placeId` and `roles` with
`connectionId`, and keep the relink warning. A trigger with the marker does not start a run, and
the step shows that it needs a link.

STOP: if a released client writes `""` to mean "any chat" on purpose in a saved graph. Then keep
`""` with that meaning and use only the new marker for transfer.

### 2. A conflict merge never saves placeholder nodes

Evidence: `src/renderer/src/features/workflows/workflows-controller.ts:379-386,406-414` merges with
`newer.graph` and saves when the canvas does not show the workflow. `newer.graph` can be the
team-client placeholder graph (`packages/team-client/src/workflow-decoding.ts:83-111`). Nothing
checks `needsNewerApp` there; the `lock` memo (`:636-644`) blocks only canvas edits.

Change: do not merge or save when the base or the newer detail has `needsNewerApp`. The host also
refuses a save that changes the kind of a node to `note` with `locked: true` when the stored node
had another kind.

STOP: none.

### 3. One bad workflow row does not break every list

Evidence: `src/backend/workflows/workflow-store.ts:508-532` (`toNode` throws "Invalid SQLite
column: workflow_nodes"); `listWithGraphs` (`:89-109`) maps all rows, so one row fails the Team API
list (`route-workflows.ts:265`). `workflow-run-store.ts:563-580` decodes run graphs strictly.

Change: decode per row. A row that does not decode gives a workflow with `needsNewerApp` and a
placeholder node, on the local desktop path too, not only in the team client.

STOP: if the change needs a migration.

### 4. Typed values fail closed at run time

Evidence:
- A missing value passes `!=`: `packages/contracts/src/ipc-workflow-answers.ts:364`.
- `templateValues` sets `""` for every source field first: `src/backend/workflows/workflow-answers.ts:66`.
- An unknown `{{name}}` stays literal in the prompt (`fillWorkflowTemplate`, `:268-271`).
- Problems from `checkWorkflowAnswer` are dropped in `givenAnswer` (`workflow-answers.ts:32`).
- A spec line with a bad type is dropped at run time; fields after the 20th are cut (audit, `:74`, `:84`).

Change: a step fails with an error that names the field when a required name has no value, when a
source failed or was skipped, or when a template name is unknown. A missing value makes every
operator false except `unset`. Starting a run is refused while the graph has answer problems.
Optional fields stay `""` only when the spec marks them optional.

STOP: if a released workflow depends on `""` for a missing required value (check the
`workflow-answers` e2e and the tool guidance).

### 5. Run input and retries use the right answer spec

Evidence:
- `run_workflow` input is not checked: `src/backend/workflows/workflow-tools.ts:797-803`. Only
  `receiveWebhook` calls `webhookAnswerEvent` (`workflows.ts:1564`).
- Run with no payload gives `""` (`triggerOutput`, `workflows.ts:1082-1088`); the Run button and
  the Team API route send no payload (audit: `workflows-controller.ts:736-743`, `route-workflows.ts:320`).
- A retry takes the current node but keeps `run.graph` (`workflows.ts:2028-2036`).
- "Run one step" reads `latestDone` from all runs (`workflow-run-store.ts:288-298`).

Change: check run input with `webhookAnswerEvent` in `startRun`, and refuse a start of a trigger
with answer fields and no valid input. A retry with a changed answer spec checks the output against
the run graph, or is refused with a clear reason. "Run one step" uses the newest attempt of each
source and fails when that attempt failed.

STOP: none.

### 6. Strict values: numbers, lists, keys, quotes

Evidence (audit A, findings 6-8, 12, 13; not checked line by line by the coordinator):
`Number(raw.trim())` accepts `0x1A`; `int` accepts `2.5`; lists render as `join(", ")`; a string
is taken as a list of one item; keys match case-sensitively and unknown keys are ignored; a spec
with only optional fields accepts prose; `'` in a check value breaks the and/or split; the approval
question shows JSON escapes.

Change: decimal pattern only, integers for `int`, safe integers only; lists render as JSON arrays
and refuse a non-array value; a reply with no JSON object is a problem; unknown or wrongly cased
keys are problems; a quote starts only at the start of a value; the human `question` field gets
plain text.

STOP: none.

### 7. A node registry in contracts drives every decoder

Evidence: the facts about each node kind are in many lists: `WORKFLOW_RUNTIME_FIELDS`
(`ipc-workflows.ts:696`), `WORKFLOW_TEMPLATE_FIELDS` (`ipc-workflow-answers.ts:273`),
`hasUnknownSetting` checks only trigger and output enums (`workflow-decoding.ts:83-88`), admin-only
types are hardcoded (`route-workflows.ts:101-130`), transfer remaps only three id fields
(`instance-transfer-workflows.ts:58-76`), runtime field lists are fixed
(`src/backend/workflows/workflow-graph.ts:8-15`). Unknown media, aspect, effort and event values run
as a different value (`workflowMediaKind`, `workflowMediaSpecs`, `workflowMediaOptions`).

Change: one registry for each kind in `packages/contracts`: fields, enum-like fields and their
values, id-bearing fields (agent, channel, connection, place, file, account), admin-only values,
template fields, runtime fields. Every decoder, the transfer remap, the admin check and the export
sanitizer read it. An unknown enum value on any field gives a placeholder and `needsNewerApp`. An
unknown admin-only value is refused by default.

STOP: if a contract change is needed on a released wire codec.

### 8. Workflow paused state

Evidence: `workflows` has no paused column (`src/backend/migrations/0046-workflows.ts:45-53`).
`create` arms schedules and GitHub watches at once (audit: `workflows.ts:1408-1416`,
`workflow-store.ts:383-391`). Duplicate copies live triggers (`WorkflowCanvas.tsx:1143-1147`).

Change (needs D1): a paused flag, a migration with data-preservation fixtures for every released
schema, a new optional capability, pause and resume in desktop, web client and mobile (mobile shows
the state), and the reverse action. Duplicate creates a paused copy.

STOP: if D1 is not given.

### 9. Format version, host enforcement and the format change rule

Evidence: no format version in `WorkflowGraph`. Capability gating is in the UI only
(`workflows-port.ts:129,131,287`), and `server-capabilities.ts:100-175` gives true when
`compatibility` is missing. Rule changes with no gate: #12954 port rules, #12944 loop start,
#12335 duration snap, #14199 resolution case. Unknown top-level properties are removed on save
(`src/main/ipc/workflow-inputs.ts:38-85`).

Change (needs D2): the host advertises `workflowFormat: <n>` through one new capability. A graph
records the format it needs. A client that does not know the format opens it read-only. The host
refuses a field or value that its format does not know. New data goes only in `fields`; a contract
test fails on a new top-level node or graph property. Add the rule to `packages/contracts/AGENTS.md`:
a new kind, value, limit or rule raises the format.

STOP: if the capability list has no free slot under the protocol limit
(`packages/contracts/src/team-protocol/capability-limits.ts`).

matching types. `edit_workflow`, `create_workflow` and start refuse these problems.
