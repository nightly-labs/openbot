## Rejected alternatives

- The central API as the owner of teams and agents: rejected. In the first
  version the API owns accounts and sessions. The host stays the owner of the
  whitelist, the roles, the agents, the conversations and the files.
- A host account with a local password: rejected. It duplicates the sign-in data
  and does not meet the requirement that the host stores neither passwords nor
  nicknames.
- Whitelisting by email text alone: rejected. The host may accept a pending
  email, but after the first valid connection it must bind the entry to a stable
  `userId` from the central API.
- A long central session token used directly by the host: rejected. The host
  gets a short, signed token with a restricted `audience`.
- 2026-10-17, considered and rejected:
  - Chat apps that only configure and do not run turns: this is by design.
  - Dead-code findings: `knip` already finds them in CI.
  - Desktop streaming updates: they are already fine-grained.
  - Refetch on each keystroke: not found in the code.
  - Moving the database dependency to Effect: the Effect migration thread owns it.
  - Persisting the Telegram context and a mailbox idempotency table now: they
    need irreversible migrations; listed above as options only.
  - Reopening plan 003 for `mcp-remote` text: the remaining references convert
    old configurations only, so plan 003 stays DONE.
