## Why this matters

- The schema changes fast: 56 migrations (v8 to v63) in about 11 weeks, two build paths for a new
  database (migrations and `LATEST_SCHEMA_SQL`), and 22 strict enum decoders (`checkedColumn`).
- The team protocol has 247 capabilities and 9 free slots under the protocol 9 limit of 256. 68
  capability files were added in the last 7 days.
- A server restarts forever after a failed start (`Restart=always`), and a desktop recovery can
  offer a release that cannot open the migrated database.
- No code reads or writes a format version for several JSON stores and for the agent-data database.

### 1. Bootstrap list stays at 64

Evidence: `TEAM_BOOTSTRAP_CAPABILITIES` has 66 entries since v0.47.0
(`packages/contracts/src/team-protocol/current.ts`, comment "A protocol 6 peer reads at most 64
capabilities"). `packages/team-client/src/remote-peer.ts` sends the list in the WebRTC request.
Hosts v0.20 to v0.34 refuse more than 64 on WebRTC (`unsupported_operation`) and, over HTTP, read
more than 64 as an empty set.

Change: freeze the bootstrap list at 64 or fewer. Put one size limit per protocol in one table, and
make a contract test fail when a list is larger than the limit of its protocol.

STOP: if a bootstrap capability is necessary for a released client, report before you remove it.

### 2. Protocol 10 with a fixed baseline (after item 1)

A new protocol version where all capabilities shipped up to now are implied by the version.
Only new capabilities go in the list. Old peers keep protocol 9 behavior.

### 3. Server start-loop guard and safe mode

Evidence: `src/main/index.ts` `recoverFromStartLoop` only logs for a server;
`scripts/hosting/openbot.service` has `Restart=always`, `RestartSec=10`;
`scripts/hosting/openbot-hosted-update` `copy_release` runs `rm -rf` before the copy.

Change: after repeated failed starts, or a `NewerDatabaseError`, the server stops the loop, keeps a
minimal Team API up that tells owners and admins the reason, and clients (desktop with a joined
server, web client, mobile) show it. The release copy becomes atomic.

### 4. Schema-aware desktop recovery

Evidence: `src/main/start-recovery-window.ts` `previousVersionUrl` links to `lastGoodVersion`
without a schema check; `src/main/newer-database-recovery.ts` installs the latest release.

Change: the recovery window offers a previous release only when that release can open the
database, or when a pre-migration copy for it exists (item 15).

### 5. Versioned JSON stores and agent-data database version

Evidence: `src/backend/sidebar-layout-store.ts` renames an unknown version to `.corrupt-<time>` and
uses the default layout, so a downgrade loses the layout. `src/backend/agent-data/agent-tables.ts`
creates `openbot_metadata` with no schema version.

Change: one helper for versioned JSON stores (keep unknown newer data, never discard it), used by
the sidebar layout and the other versioned stores; a schema version and a newer-version guard for
the agent-data database.

### 6. Database instances and version comparison

Evidence: `src/backend/mailbox-store.ts` and `src/backend/agent-store.ts` default to
`new OpenBotDatabase(userDataPath)`. Four release comparators differ: `update-service.ts`
`isNewerRelease`, `host-release-service.ts` `newerRelease`, `packages/contracts/src/mobile-features.ts`
`isNewerMobileVersion`, and `newer()` in `scripts/hosting/openbot-hosted-update`.

Change: inject the database; one shared comparator for TypeScript, with a shared fixture that the
bash function must also pass. Fix the hosted auto-install docs if they disagree with
`requested-update.ts`.

### 15. Pre-migration copy

PR #7150 (draft) runs `VACUUM INTO` before the first pending migration, keeps 2 copies, and skips
the copy when the disk is too full. The NorbiAI P1 finding is the conflict with the
non-negotiable "No backup of `openbot.db` is made before an upgrade" (`AGENTS.md`,
`src/backend/AGENTS.md`). The measured cost is 0.46 s for 385 MB. To merge it, the developer must
decide to change that rule.
