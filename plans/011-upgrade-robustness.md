## Why this matters

- The schema changes fast: 56 migrations (v8 to v63) in about 11 weeks, two build paths for a new
  database (migrations and `LATEST_SCHEMA_SQL`), and 22 strict enum decoders (`checkedColumn`).
- The team protocol has 247 capabilities and 9 free slots under the protocol 9 limit of 256. 68
  capability files were added in the last 7 days.
- A server restarts forever after a failed start (`Restart=always`), and a desktop recovery can
  offer a release that cannot open the migrated database.
- No code reads or writes a format version for several JSON stores and for the agent-data database.

## Support window (developer decision, 2026-11-17)

- **Apps and protocols**: desktop, hosts and the web client support the releases of the last 2
  months (60 days; first decided as 14 days, then changed the same day). Mobile has at least 2 months.
  A peer outside the window gets "update required". Its adapters,
  codecs, fixtures and capabilities can be deleted. The rule is in `AGENTS.md` and
  `packages/contracts/AGENTS.md`; it replaces "Released Team API adapters are permanent".
- **Migrations**: not in the window. A database from any shipped release still upgrades with no
  data loss. Every migration and its fixtures stay.
- **Forced update**: the account service publishes a minimum version for each surface. An older app
  shows a blocking "Update required" screen and installs the update (item 24). The minimum does not
  move by itself (developer decision, the same day): the PR that deletes old code or needs it raises
  the minimum, and CI refuses a minimum that is less than 60 days old. The window is a floor, not a
  daily trigger.
- **Pre-migration copy**: dropped (developer decision, the same day, after the hosted size check). The
  rule "No backup of `openbot.db` is made before an upgrade" stays. Migrations must be safe by
  themselves: items 7 to 10 and 12 come first.

Host protocol by release: V4 from v0.7.0, V5 v0.24.0 (09-28), V6 v0.31.0 (10-07), V7 v0.35.0
(10-10), V8 v0.48.0 (10-22), V9 v0.55.0 (10-30). Mobile 1.4.3 (10-29 to 10-31) is the last protocol 8 mobile
build, and mobile checks only that the host range includes protocol 3. With 60 days, hosts that read at
most 64 capabilities (v0.20 to v0.34.1) stay in the window until about 2026-12-09, so item 1 is needed.

### 1. Bootstrap list stays at 64

Evidence: `TEAM_BOOTSTRAP_CAPABILITIES` has 66 entries since v0.47.0
(`packages/contracts/src/team-protocol/current.ts`, comment "A protocol 6 peer reads at most 64
capabilities"). `packages/team-client/src/remote-peer.ts` sends the list in the WebRTC request.
Hosts v0.20 to v0.34 refuse more than 64 on WebRTC (`unsupported_operation`) and, over HTTP, read
more than 64 as an empty set.

Change: freeze the bootstrap list at 64 or fewer. Put one size limit per protocol in one table, and
make a contract test fail when a list is larger than the limit of its protocol.

STOP: if a bootstrap capability is necessary for a released client, report before you remove it.

### 2. Minimum protocol follows the window, then protocol 10 with a fixed baseline

Step 1: for each protocol, find the last release of each surface (desktop, host, web client, mobile)
that speaks it, and the date it leaves the 60-day window. Raise the minimum and delete the codecs,
adapters and fixtures only for protocols that no release in the window speaks. A host refuses an
older client with `client_update_required`; a client refuses an older host with
`host_update_required`. Expected order: protocols 1 to 3 (check the mobile protocol 3 use first),
then 4 and 5, then 6 and the bootstrap list after about 2026-12-09, then 7 and 8 after about
2026-12-31 (mobile 1.4.3).

STOP: if a release in the window, or a mobile store build in the mobile window, speaks a protocol
that the change deletes.

Schedule result (delegate, checked on `origin/main`, 2026-11-17). Protocol 4 starts in v0.7.0, not
v0.8.0. The last release of a protocol leaves the 60-day window on these dates:

| Protocol | Out of the window |
|---|---|
| 4 | 2026-11-26 |
| 5 | 2026-12-04 |
| 6 | 2026-12-08 |
| 7 | 2026-12-20 |
| 8 | 2026-12-28 (desktop and hosts), 2026-12-30 (mobile 1.4.3) |

No protocol can be deleted yet, because a raised minimum does not make an old peer show "update
required":

- Every release advertises minimum 1. Mobile 1.1.0 to 1.4.10 and the web client check only that the
  host range includes protocol 3, so a host with minimum 9 is refused by all mobile builds.
- The host WebRTC peer maps an unmarked request to protocol 3 or 1, and the v4 and v5 adapters use
  the v3 request codec. All WebRTC frames use the protocol 2 framing.

Prerequisite steps, in this order:

1. Mobile (also the share sender) and the web client compare the host range with their real range.
   This ships first, and the minimum moves only after these builds are in the window.
2. Move the protocol 2 framing and the v3 GET codec into the current adapter, so that deleting the
   old adapters does not delete code that the current protocol uses.
3. The host refuses an unmarked WebRTC request with `client_update_required`.

Not confirmed: mobile store release dates (the repo has only the prepare commits), the mobile window
policy (no repo source), and whether the web client is served from the latest `main`.

Step 2: protocol 10 (`packages/contracts/src/team-protocol/v10.ts`) has a fixed capability baseline,
the frozen protocol 9 list (`fixtures/v10/baseline-capabilities.json`). A protocol 10 peer sends two
lists, in both directions: `capabilities`, with the names after protocol 9 and the markers, and
`absent`, with the baseline names that it does not serve. The receiver's set is
`(baseline - absent) + capabilities`. The version does not imply a baseline capability, because a
peer can lack one: a Mac host does not serve `mac-apps-limit-v1`, and a host with no channel service
does not serve the channel capabilities. A host ignores an unknown name in `absent` and refuses a
malformed list with `protocol_error`. `absent` has at most as many names as the baseline. Protocols
1-9 do not change. The host speaks 1-10; the desktop and web clients speak 10 when the host does, and
mobile stays on 9 until a capability after protocol 9 needs it there. When no release in the window
speaks protocol 9, the baseline stays: it is the protocol 10 wire contract.

The protocol 9 list is full since #11930 (2026-11-18): 256 of the 256 capabilities that it can
have. A new optional capability needs protocol 10 first.

### 14. Projection check and transfers sweep (re-scoped)

Measured on 2026-11-18 on a read-only copy of one real desktop profile (the developer's; schema 63,
8 threads, 9,666 events). Counts only.

- **Replay is not a correct copy.** No production code calls `ThreadReplay.rebuildThreadProjection`;
  only E2E scripts do. A rebuild changes the saved rows: `projection_turns.provider_session_id`
  becomes null in almost every turn, 4 failed or interrupted turns become `completed`, 9 turns are
  added, 2,011 of 2,274 messages in one thread move, and most turn times move by less than 5 s. No
  message is lost or added, and no message content changes. So a check against the replay reports
  every thread, and a repair from the events would damage data.
- **Saved rows hold simple rules.** Each active turn exists, no running turn is without an active
  turn, ordinals are unique, no message is without a thread, and `PRAGMA foreign_key_check` is
  clean. 2 of 22 `thread-message` attachment rows have no message. These rows have an empty `path`
  by design (`conversation-writer.ts`).
- **A transfers sweep is not safe.** The desktop app and every dev profile use the same
  `~/OpenBot/Shared/Transfers` (`openbotRoot` in `agent-store.ts`). On the measured computer, 391
  profile databases use it and 330 name entries in it. The production profile names none of the
  11,462 `generated/` entries; dev profiles name 4,280 of them. A sweep that deletes the entries one
  database does not name deletes files that another profile uses. No `.tmp-*` folder was left.

Decision: no delete sweep, and no check against the replay. Make the replay keep turns, sessions
and message order first, and only when a repair path needs it. Not confirmed: other users and
hosted servers. Only one computer was measured.

### 16. Update state audit (re-scoped)

Audited on 2026-11-18: the desktop `UpdateService`, the hosted and container update scripts, and the
macOS Host Manager. Each claim below was checked in the code.

- **Fixed.** When a Host Manager takes over the updates, the tenant cancels its own check and
  download and shows no busy phase (`setManagedByHost`, `scripts/update-host-takeover-e2e.ts`).
  Before, a running download continued, and its events replaced the host state until the next poll.
- **Not a defect.** A torn `staged.ready` reads as "not staged", and the next `stage` removes the
  copy and stages it again, so an atomic write changes nothing. After a newer download replaces a
  ready update, electron-updater has cleared the old file (`AppUpdater.js`, `DownloadedUpdateHelper.js`),
  so "ready" cannot come back. `availableVersion` in `error` is the version that a download retry
  uses (`#canDownload`), and mobile shows it. The macOS `failed` phase stops tenant starts by design,
  and `docs/multi-tenant-hosting.md` "State and recovery" gives the admin reset. The three other
  `sort -V` copies compare validated `X.Y.Z` versions only, as the tested bash `newer()` does.
- **Not worth a union type.** `UpdateStatus` is also the server update status that mobile and the
  web client read, and the loose fields have no defect left after the items above.
- **Open, needs a decision.** The install result of a hosted server is not saved or reported (no
  code reads `.applying`). Reporting it needs a new optional capability, and the protocol 9 list is
  full (item 2). The four "run started" files (`start-attempts`, `run-marker`, `startup-history`,
  `gpu-start`) can become one versioned file, but released versions read them, so this needs its own
  upgrade plan.

### 20. Separate database for tables that can be rebuilt (dropped)

Audit of 2026-11-18 (`main` at `6a5f3fab5b`):

- **Few tables can be rebuilt.** The `projection_*` tables are the source of truth: the thread replay
  (`thread-replay.ts:41`) and `ChannelStore.rebuild` (`channel-store.ts:1113`) have no production
  caller. Only the FTS index `agent_memory_search` and the provider history staging cache can be
  rebuilt, and both are small.
- **`orchestration_events` is not a full event log.** The code deletes old events (for example
  `agent-roster.ts:399-402`, `conversation-writer.ts:1042`, `memory-store.ts:298-312`), and production
  code reads events (`agent-roster.ts:110`, `routine-store.ts:207`, `hosted-site-event-log.ts:71-135`).
- **Item 23 (#11872, v0.73.0) already removes most of the size.** On a copy of the developer's
  profile: `orchestration_events` 326.3 MB to 32.3 MB, in 1.6 s. The file stays 384.8 MB because the
  free pages stay in it; `VACUUM INTO` gives 88.8 MB.
- **A second file costs too much.** `dispatch` writes events, projections and the receipt in one
  transaction (`database-core.ts:139-191`); across two WAL files a commit is atomic for each file only
  (SQLite documentation), so a crash can run a retried command two times, and privacy deletes
  (`deleted-thread-messages.ts:105-134`, `agent-roster.ts:178-243`) can leave deleted text. Migrations,
  the frozen-file check, the harness, the 42 released schema fixtures, backups and hosted saves all
  work on one file. The move copies about 12 GB on the largest hosted server.

Item 26 takes the real gap that is left: the file does not get smaller on disk. A one-time `VACUUM`
needs about 2x the file in free disk and holds the write lock for its full time; measure it with
`bun scripts/migration-large-db-e2e.ts --full` on a large server first. Not confirmed: hosted
servers after v0.73.0 were not measured.

### 22. Routes E2E split (not done)

Measured on 2026-11-18 (`main` at `641fc1e429`):

- **No CI gain.** The file has 14,263 lines, but the `Team API routes E2E` job takes 39 s (with
  the CRM and comparator scripts), and `Check` takes about 4 min. The job is not on the critical path.
- **The size causes no merge conflicts.** 104 commits changed the file in 30 days. Of the 6 open PRs
  that change it, `git merge-tree` with `origin/main` finds a conflict in it for 1 PR only (#8198,
  which also has conflicts in many other files). A split moves each line, so all 6 PRs would get a conflict.
- **The checks are one sequence.** Lines 2336-14252 are one `try` block on one server, and later
  checks read stand-in state that earlier checks wrote. Separate scripts would each need the 2,300
  lines of stand-ins, or a shared context module that only moves the code.

Do instead: give a new route area its own script, as `scripts/crm-team-api-e2e.ts` does for `crm-v1`.
Open this item again when the job time is on the critical path, or when conflicts in the file are
frequent.
